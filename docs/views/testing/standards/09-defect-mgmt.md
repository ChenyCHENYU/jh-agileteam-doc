# 缺陷管理规范

> 📦 来源：`wl-skills-test` v0.11.0 · `standards/09-defect-mgmt.md` · 可判定条目由 `wl-skills-test audit`（T 系列）与 `gate` 自动执行。


## 适用范围

本规范适用于测试过程中缺陷（BUG）的录入、分级、跟踪与回归。所有缺陷必须在缺陷管理平台登记，不得口头沟通了事。

## BUG 录入规范

每条 BUG 必须包含以下要素：

| 要素 | 要求 |
| --- | --- |
| 问题描述 | 清晰、简洁，一句话说明现象 |
| 复现步骤 | 具体、有序、可复现 |
| 产品 | 选择对应产品 |
| 功能 | 选择对应功能模块 |
| 版本 | 选择发现版本 |
| 接口报错 | 贴请求与返回日志 |
| 前端现象 | 截图并标注问题位置 |
| 严重程度 | 按分级标准选择 |
| 优先级 | 按修复紧急程度选择 |

## 录入要求细则

### 问题描述

- 禁止"功能有问题""报错了"等模糊描述。
- 必须说明在什么前置下、做了什么操作、出现了什么异常。

### 复现步骤

- 按顺序编号，每步一个动作。
- 包含前置条件（账号、数据、环境）。
- 可被他人按步骤复现。

### 接口报错

- 贴出请求 URL、请求参数、返回状态码、返回 body。
- 标注期望返回与实际返回的差异。

### 前端截图

- 截图必须标注问题位置（圈出 / 箭头）。
- 包含浏览器控制台报错截图（如有）。

## 严重程度分级

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| 致命 | 系统崩溃、核心功能不可用、数据丢失 | 登录不了、下单报 500 |
| 严重 | 主功能异常、有规避但影响业务 | 列表不刷新、计算错误 |
| 一般 | 次要功能异常、有规避 | 某筛选项失效 |
| 轻微 | UI、文案、体验问题 | 错别字、对不齐 |

## 缺陷生命周期

```
新建 → 指派开发 → 开发修复 → 测试回归 → 关闭
                                    ↓
                               回归失败 → 重开
```

## 回归测试规则

| 规则 | 说明 |
| --- | --- |
| 回归时机 | 穿插在两轮全量执行中，不单独成轮 |
| 回归范围 | 修复缺陷 + 关联功能 + 影响范围 |
| 回归工作量 | 全量工作量的 50% |
| 争议处理 | 有争议拉产品讨论，不得私下关闭 |

## 争议处理

- 测试与开发对缺陷等级、是否为缺陷有争议时，拉产品共同讨论。
- 讨论结论记录在缺陷备注中。
- 不得未经讨论单方面关闭或拒绝缺陷。

## 示例（合格 BUG 录入）

- 标题：订单列表筛选"已支付"状态后，列表不刷新。
- 产品：订单系统。
- 功能：订单列表 - 筛选。
- 版本：v2.3.0。
- 前置：使用测试账号 AT_user01 登录，存在已支付订单。
- 步骤：1. 进入订单列表 2. 状态筛选选择"已支付" 3. 点击查询。
- 预期：列表只展示已支付订单。
- 实际：列表展示全部订单，未按筛选过滤。
- 接口：GET /api/orders?status=paid 返回全部订单（贴日志）。
- 截图：（标注筛选条件与列表结果）。
- 严重程度：严重。

## 注意事项

1. 一条 BUG 只描述一个问题，禁止合并多个问题。
2. 无法复现的缺陷标注"偶发"，保留日志并持续观察。
3. 缺陷关闭必须由测试验证后操作，开发不得自行关闭。
4. 缺陷来源需标注（需求 / 设计 / 编码 / 环境），用于根因分析。
5. 重复缺陷及时合并，避免重复跟踪浪费资源。
