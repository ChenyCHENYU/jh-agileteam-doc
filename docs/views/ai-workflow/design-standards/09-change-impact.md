# 09 — 变更影响分析规范

> 📦 来源：`wl-skills-design` v0.11.1 · `standards/09-change-impact.md` · 可判定条目由 `verify`（[M] 机械项）自动执行。


> 目标：把设计变更从“人工记忆同步”升级为“先分析影响，再补丁更新，最后复验闭环”。

---

## 一、适用范围

当用户提出以下需求时使用本规范：

- 已有设计文档上新增、删除、重命名字段
- spec 处理逻辑、状态机、按钮、校验规则发生变化
- 数据库表字段、枚举、索引、状态值发生变化
- 接口请求/响应字段、错误码、幂等、安全规则发生变化
- 原型页面字段、按钮显隐、交互状态发生变化
- 术语词典需要新增或统一命名

本规范不直接替代各单域生成规范；它负责**跨产物影响判断和补丁计划**。

---

## 二、变更输入结构

每次分析必须先形成一条变更登记：

| 项 | 必填 | 说明 |
|----|------|------|
| 变更编号 | 是 | `CHG-YYYYMMDD-序号` |
| 变更来源 | 是 | 业务需求 / 评审问题 / 开发反馈 / 测试缺陷 |
| 变更对象 | 是 | 字段 / 状态 / 按钮 / 流程 / 表 / 接口 / 页面 / 词条 |
| 变更动作 | 是 | 新增 / 修改 / 删除 / 重命名 / 拆分 / 合并 |
| 当前描述 | 否 | 变更前内容 |
| 目标描述 | 是 | 变更后内容 |
| 涉及模块 | 是 | 模块名、功能编码、页面编码、接口编码等 |
| 已知文档路径 | 否 | spec / DB / API / prototype / glossary 路径 |

缺少“变更对象、变更动作、目标描述”时，不得继续分析，先追问。

---

## 三、影响域

| 域 | 检查重点 | 常见补丁 |
|----|----------|----------|
| spec | IPO 字段、处理逻辑、状态机、画面对照、内部接口 | 更新功能章节、IPO、状态机、画面对照 |
| glossary | 中英文名、枚举值、编码、同义词 | 新增词条、合并同义词、统一字段英文名 |
| DB | 表字段、类型长度、索引、默认值、枚举、历史字段 | 新增/修改字段、索引、DDL、数据字典 |
| API | 请求/响应字段、错误码、幂等键、安全说明 | 更新接口定义、OpenAPI、错误码 |
| prototype | 页面字段、按钮、显隐规则、字典编码、状态文案 | 更新页面标注、交互规则、data-* 锚点 |
| review | P0/P1 问题、追溯矩阵、评分 | 重新执行集成评审 |

---

## 四、影响传播规则

### 字段变更

```
glossary 字段词条
  → spec IPO 字段
  → DB 数据字典 / DDL
  → API 请求响应字段
  → prototype 字段标注
  → design-review 追溯矩阵
```

### 状态机变更

```
spec 状态机
  → glossary 枚举
  → DB 枚举默认值 / 约束
  → API 状态字段 / 错误码
  → prototype 按钮显隐 / 标签文案
  → review P0/P1 门禁
```

### 接口变更

```
API 字段 / 错误码 / 幂等
  → spec 内部接口与处理逻辑
  → DB 字段落库或查询来源
  → prototype 操作按钮和反馈文案
  → review IF-X / D4 复验
```

### 原型变更

```
prototype 字段 / 按钮
  → spec IPO 字段和处理逻辑
  → glossary 字段词条
  → DB/API 是否需要承载
  → review PT-X / D4 复验
```

---

## 五、输出格式

每次必须输出以下 5 段：

1. **变更登记**：按第二节表格填写
2. **影响矩阵**：按域列出影响等级、原因、需改文件、责任 Skill
3. **补丁任务清单**：按 P0/P1/P2 排序，明确先后依赖
4. **建议执行顺序**：指定应调用哪些已发布 Skill 复验
5. **阻断项**：列出无法继续的缺失文档或歧义输入

---

## 六、影响等级

| 等级 | 含义 | 处理要求 |
|------|------|----------|
| P0 | 不同步会导致开发不可用或数据不一致 | 必须先修复再交付 |
| P1 | 会导致评审失败或字段追溯断裂 | 本轮必须修复 |
| P2 | 文档质量、说明完整性、体验一致性问题 | 可排入后续补丁 |
| NA | 无影响 | 说明判断依据 |

---

## 七、补丁任务格式

| 优先级 | 任务 | 文件 | 责任 Skill | 前置依赖 | 完成标准 |
|--------|------|------|------------|----------|----------|
| P0/P1/P2 | 动词开头 | 相对路径 | manifest 中的 Skill id | 依赖任务编号 | 可验证条件 |

任务必须能被执行，禁止只写“完善文档”“同步相关内容”。

---

## 八、闭环流程

```
[阶段1] 生成影响矩阵
      ↓
[阶段2] 验证影响覆盖：spec / glossary / DB / API / prototype / review 是否逐域判断
      ↓ 有缺口？
[阶段3] 修复补丁计划：补齐遗漏域、依赖顺序、责任 Skill
      ↓
[阶段4] 复验：P0/P1 均有任务或 NA 理由 → ✅ DONE
```

---

## 九、验证清单（CI-A/B/C/X）

### CI-A 输入完整性

- [ ] A01 变更对象明确
- [ ] A02 变更动作明确
- [ ] A03 目标描述明确
- [ ] A04 涉及模块或功能编码明确

### CI-B 影响覆盖

- [ ] B01 spec 已判断
- [ ] B02 glossary 已判断
- [ ] B03 DB 已判断
- [ ] B04 API 已判断
- [ ] B05 prototype 已判断
- [ ] B06 review 已判断

### CI-C 补丁可执行

- [ ] C01 每个 P0/P1 影响都有补丁任务
- [ ] C02 每个补丁任务有文件路径
- [ ] C03 每个补丁任务有责任 Skill
- [ ] C04 任务依赖顺序无循环
- [ ] C05 完成标准可验证

### CI-X 跨文档一致性

- [ ] X01 字段变更使用 glossary 作命名锚点
- [ ] X02 状态变更同步 spec 状态机、DB 枚举、API 字段、prototype 显隐
- [ ] X03 接口变更回写 spec 内部接口和 DB 来源
- [ ] X04 原型新增字段不越过 spec/glossary 直接进入页面
- [ ] X05 最终建议包含对应 validate prompt 或 design-review 复验

---

## 十、修复协议

发现失败项时按以下顺序修复：

1. A 组缺失：先追问用户，不得猜测
2. B 组缺失：补齐影响域判断
3. C 组缺失：把笼统建议拆成可执行任务
4. X 组缺失：补跨文档联动和复验入口

有 A01/A02/A03 失败时，状态必须为“阻断”；有 P0/P1 未形成补丁任务时，状态必须为“需修复”。
